## 案例一：章边界丢条——状态机的收尾路径少走了一半

### 症状：数字对不上

语料管线首跑，`parse_minfadian()` 打印"解析条文 **657** 条"。而民法典三编的官方条数是
公开事实：**700** 条（合同 526 / 婚姻家庭 79 / 侵权责任 95）。`grep -c
"^第[一二三四五六七八九十百千零]*条" raw/minfadian_full.txt` 也是 700。**差 43 条**，
且解析过程零报错——这是最坏的一种 bug：静默丢数据。

### 最小复现

先排除"单行识别"问题：把三个正则（编/章/条）逐条喂给缺失条的原文行，全部正常命中。
问题必然出在**行与行之间的状态流转**上。于是做最小样本——从语料中截取缺失条
"第一千一百七十八条"前后共 9 行（`raw/minfadian_full.txt` 第 1061~1069 行），蒸馏成：

```text
第一千一百七十六条 自愿参加具有一定风险的文体活动……
第一千一百七十七条 合法权益受到侵害，情况紧迫……
第一千一百七十八条 本法和其他法律对不承担责任或者减轻责任的情形另有规定的，依照其规定。
第二章 损害赔偿
第一千一百七十九条 侵害他人造成人身损害的……
```

修复前的解析器对它输出 3 条：1176、1177、**1179**——恰好缺 1178。它是（侵权责任编
第一章的）最后一条，处于 pending 状态时撞上"第二章"标题行，被当成"上一章的脏状态"
清掉了；1179 正常入库，把缺口掩盖得毫无痕迹。全量同理：语料共 50 个边界（3 编 +
47 章/分编），其中 43 个边界撞上时存在 pending 条文 → 丢 43 条（合同 29 / 婚姻家庭 5 /
侵权责任 9），另 7 个边界（文件头、标题连续出现处）当时无 pending 才幸免。

### 根因

解析器是两状态机：`current` 在遇到**下一条条文**时才 `articles.append(current)` 收尾。
但编/章标题分支只写了 `current = None`——一类转移只更新自己关心的状态（book/chapter），
把另一个活跃状态（未落账的 current）顺手丢弃。**收尾路径 = 循环退出 + 所有边界转移**，
而边界转移这条路径从没被执行过收尾逻辑。

### 修法与验证

每个边界分支先收尾再重置（`app/scripts/ingest_laws.py` 现状）：

```python
if m:  # 编边界
    if current:            # 先收尾当前条文（否则每编/章的最后一条被丢）
        articles.append(current)
        current = None
    book = m.group(1).strip()
    continue
```

章/分编边界同样处理。验证三层：①重跑管线打印 700 条且每编 526/79/95；②守恒校验
（解析条数 == md 中条数 == 700）；③回归测试
`test_parse_all_700_articles` 用官方数字做**外部锚点断言**。注意一个陷阱：管线自带的
"条文守恒"校验抓不到这个 bug——它比的是"解析条数 vs 写入条数"，两者同源，解析端丢的
md 端同样没有，守恒依然成立（详见 [02语料管线](02-语料管线-ingest.md) 第 2 节）。

### 通用教训

- 状态机解析器的收尾路径 = 循环退出 + **所有**边界转移。测试只喂"标准序列"时，
  边界路径永不触发——测试要专门构造"章末条 + 章标题"的相邻样本。
- 同源校验只能抓"解析→写入"环节的丢失，抓不了"解析→解析"环节的丢失；能兜底的
  是外部锚点（官方总数）与序列性质检查（同编内条号差恒为 1，丢条处必现跳跃 …467, 469…）。
- 迁移价值：任何"逐行/逐事件累积、遇标记切换上下文"的解析器（日志、聊天记录、
  法律/医疗文书）都有同款陷阱。

## 案例二：中文数字转换连环坑——"看起来简单"的规则藏着文化

### 症状：一个 bug 修出另一个 bug

第一幕：`query_law_article("第1062条")` 查不到（README 的演示问题之一）。工具层的
归一化函数 `_num2cn` 只有百位分支：`_CN = "零一二三四五六七八九"` 共 10 个字符，
`_num2cn(1062)` 算到 `head = _CN[n // 100]` 时 `_CN[10]` 直接
**IndexError: string index out of range**——千位条号越界，工具报错，Agent 侧表现为查询失败。

第二幕：补上千位分支后再测，又错一片：`num2cn(110)` 输出"**一百零十**"（正确是
"一百一十"）；第一版千位分支还把 1091 拼成"一千九十一"（丢"零"；补上 rest<100 插零后
1091 对了，但 1010 仍是"一千零十"，缺"一"）。这些错误字符串与 `LAW_ARTICLES` 的
中文键（"第一千零六十二条"）对不上，查询继续失败。

### 最小复现

```python
>>> num2cn(110)   # 修复前（git show 635eab2:app/agent/rag/lawref.py 可复验）
'一百零十'
>>> num2cn(1010)
'一千零十'
>>> _num2cn(1062) # 更早的 law.py 版本
IndexError: string index out of range
```

### 根因

中文数字**不是位置计数**："一十"的"一"在 10~19 必须出现（一百一十、一千零一十），
"零"的插入取决于高位是否为零（一千零九十一 vs 一千九百一十一）——这些是文化书写规则，
不是除法取模能自然得出的。雪上加霜的是**同一逻辑存在两份实现**：`law.py` 的
`_num2cn`（Phase 1）与 `lawref.py` 的 `num2cn`（升级第三步新建），各自演化、各自带 bug，
修一处漏一处——双副本漂移的实证。

### 修法与验证

5554508 一次性解决两件事：**合并实现**（law.py 删掉副本，改
`from app.agent.rag.lawref import num2cn`，转换逻辑全仓库唯一）+ **规则修正**：
百位余数 10~19 补"一"（`head + "一" + num2cn(rest)`）；千位余数 <100 补"零"、其中
10~19 再补"一"。验证是本案例的教学核心，三层递进：

1. **全量回环断言**：`for n in range(1, 1261): assert cn2num(num2cn(n)) == n`
   ——1260 是民法典总条数，穷举而非抽样，0 失败。
2. **样例人工核对**：1010=一千零一十、1091=一千零九十一、110=一百一十。为什么回环
   不够还要人工？实测发现 `cn2num` 是**宽容解析**（"零"不校验位置、"十"前缺"一"也能
   算对）：`cn2num("一百零十") == 110`、`cn2num("一千零十") == 1010`——**回环只能证明
   "无信息丢失"，不能证明"符合中文书写规范"**，错误的字符串照样回环成功。
3. **语料交叉验证**：对语料中全部 700 个条号 n，断言 `第{num2cn(n)}条` 能在
   `raw/minfadian_full.txt` 原文中找到——官方文本就是标准答案，0 不匹配。

回归测试落在 `tests/test_graph_nli.py::TestLawRef`（`test_num2cn_roundtrip` 采样
10/188/680/1062/1258 + `test_cn2num` 含 1091 用例）。

### 通用教训

- "人人都会念"的转换恰恰最容易写错：规则长在文化里而不是代码里。等价类要用**穷举**
  （值域只有 1260 个，穷举成本为零）而非抽样覆盖；穷举之外还要补"回环测不出"的
  规范性核对，最好找到**官方语料当标准答案**做交叉验证。
- 同一逻辑两份实现必然漂移——发现即合并，集中一处，让"改一处生效两处"。

## 案例三：CI 由红转绿——本地全绿 ≠ CI 绿

### 症状：push 之后脸疼

本地 `pytest` **109 个测试全绿**，push。GitHub Actions 变红。同一份代码，两个环境，
一个绿一个红——问题必然出"本地没跑过的东西"上。

### 最小复现与排查

看 Actions 失败日志：挂掉的不是 pytest 步骤，是 CI 的**第二条命令**——
`Retrieval quality guardrail (offline)`，启动约 1 秒即崩，Traceback 是
**NameError: name 'settings' is not defined**。本地没发现的原因极其朴素：
**本地只跑了 `pytest`，从没在本地跑过 CI 里的第二条命令**
（`python -m app.scripts.run_retrieval_eval --strict`）。

引入过程（953f8e4）：审查指出 `evaluate()` 里硬编码
`get_bm25(str(_P("app/agent/rag/knowledge")))`，我改成读配置 `settings.kb_dir`——但
`settings` 是 `main()` 里的局部变量，`evaluate()` 根本引用不到。更隐蔽的是，这行代码
在 `mode == "hybrid"` 分支里：baseline、rerank 两轮评估正常跑完，第三轮 hybrid 才炸。
import 期不报错、部分执行不报错——**静态可见性问题和运行时作用域问题叠加**，
pytest 对这个脚本零覆盖（它是脚本不是模块），于是本地全绿。

### 根因

重构把"硬编码路径"改成"注入配置"时，只改了引用处，没改数据流：`settings` 没有
作为参数流进 `evaluate()`。CI 门禁有两条命令，本地验证只覆盖了一条。

### 修法与验证

`evaluate(retriever, entries, mode, settings=None)` 加形参，`main()` 调用处传入
（13539a5 的 #13，内部兜底 `settings or Settings()`）。CI 时间线是最终验证，红绿
对比至今可查：

| push | CI | 失败步骤 |
|---|---|---|
| 953f8e4（10-01，引入 NameError） | 红 | Retrieval quality guardrail（约 1 秒崩） |
| 5917ebc（10-01，修的是另一个 bug） | 红 | 同上——NameError 仍在 |
| 13539a5（10-02，#13 修复） | **绿** | —— |
| 312349f（10-07 及以后） | 绿 | —— |

红窗约 26 小时、跨 2 次 push——期间每次"本地绿"都只是心理安慰。

### 通用教训

- **CI 里的每条命令都必须在本地逐条执行过**。"pytest 全绿"只覆盖门禁的一半；
  `--strict` 这类质量护栏脚本同样会崩，且不在任何测试的势力范围内。
- 重构"硬编码 → 配置注入"时，检查的是**数据流**（谁定义、谁传参），不是单个引用。
- 运行时才求值的引用（分支深处引用外层局部名），import 检查和常规测试都抓不到——
  让 CI 替你把"从没走过的路径"走一遍，正是 CI 的价值。

## 案例四：heredoc 转义连环坑——"脚本跑完了" ≠ "补丁打上了"

### 症状：批量补丁的静默失败

工程环境问题（Windows + Git Bash）。多次用 bash heredoc 批量打 Python 补丁，出现两类
症状：①写出的 .py 文件字符串里 `\\n`/`\\d` 被 Git Bash **静默吃掉一层转义**，字符串
里出现真实换行或损坏内容，导入即 SyntaxError；②更阴险的一类——替换 pattern 因为
转义变形后**根本没命中**，脚本却正常 exit 0，"替换悄然没打上"。

### 最小复现（一次有完整 git 铁证的失败）

953f8e4（外部审查校准修复）的提交说明里明确列出"long_term.py build_prompt_section
向模型注入'过敏史/用药咨询'医疗话术（复用残留中唯一有语义影响的一条）"已修。但：

```bash
$ git show 953f8e4 --stat        # 8 个文件落账，没有 app/agent/memory/long_term.py
$ git show 953f8e4:app/agent/memory/long_term.py | grep 用户健康档案
    return ("## 用户健康档案（长期记忆，用药咨询前必须核对过敏史与在用药品）\n" ...
```

**宣称修了、diff 里没有、旧文本还在库里**——heredoc 补丁静默失败，批次里其余修复
落了账，唯独这一处没落，没有任何报错。靠事后逐条 grep 幂等标记（查"用户健康档案"
仍命中）才发现，51 秒后用编辑器精确重修落地，即 5917ebc，提交标题自带结论：
"long_term.py 注入话术修复落地(**前次heredoc转义未打上,Edit重修**)"。同一晚的审查
会话里 shell 甚至故障到 DLL_INIT_FAILED、连 git/pytest 都跑不了，直接导致审查方
3 条误判（953f8e4 提交说明"误判澄清"一节有记录）——**shell 本身就是被诊断对象**。

### 根因

Git Bash 对 heredoc 内容做多一层转义解释，`\\n` 变成真实换行、`\\d` 变成 `d`；
替换类补丁"未命中"不产生任何错误信号（脚本语义上"没找到就没替换"，exit 0 合法）。
自动化修改工具的失败模式是**静默的**，而人默认"脚本跑完 = 任务完成"。

### 修法与验证

三道闸，此后批量修改再没丢过补丁：

1. **关键替换全部改用编辑器精确编辑**（所见即所得，不做转义中介）。
2. 补丁脚本加 **assert 锚点**：每次替换前断言目标文本存在、替换后断言新文本存在、
   旧文本消失——未命中立即中断报错，而不是静默跳过。
3. 修完用**幂等标记 grep 核查清单**：每处修改登记一个可 grep 的标记串，逐一核对
   "新标记在、旧标记无"，全过才算完（本案例正是靠它抓回 long_term.py）。

### 通用教训

- 批量自动修改必须有**锚点断言 + 事后核查**两道闸："脚本跑完了" ≠ "补丁打上了"，
  "commit message 写了" ≠ "diff 里有"（本案例的提交说明与 diff 就公开打架）。
- 迁移价值：适用于一切"用脚本改代码/改配置"的场景——sed、正则替换、Codemod、
  数据库迁移脚本，凡静默跳过不报错的工具都需要外置的验证闭环。
- 环境本身也可能生病：当工具链出现无法解释的行为时，先换一条已验证的通路
  （编辑器 / 另一个终端）把工作落地，再回头追环境问题。

## 调试工具箱：本项目验证过的排查手段

| 手段 | 一句话用法 | 首次见效 |
|---|---|---|
| **最小样本复现** | 把失败输入二分到"再删一行就不复现"：9 行样本让 43 条丢失变成肉眼可读的 1 条（案例一） | 案例一 |
| **数字锚点对账** | 程序内统计与外部权威数字（官方 700 条）对不上 = 报警，哪怕零报错（案例一） | 案例一 |
| **全量回环断言** | 值域有限的双向转换用穷举回环：`for n in range(1,1261): assert cn2num(num2cn(n))==n`（案例二） | 案例二 |
| **回环盲区意识 + 样例人工核对** | 宽容解析让错误输出也能回环成功，规范正确性要拿样例/官方语料交叉验证（案例二） | 案例二 |
| **CI 命令本地逐条跑** | 门禁有几条命令，本地就逐条跑几条；"pytest 绿"只是一半（案例三） | 案例三 |
| **干净环境验证** | CI（Linux/全新依赖）是一条免费干净环境；本地"复现不了"先怀疑环境差异（案例三） | 案例三 |
| **幂等标记核查清单** | 每处批量修改登记可 grep 的标记，事后逐一核对"新在旧无"（案例四） | 案例四 |
| **锚点断言的补丁脚本** | 替换前后都 assert 目标文本状态，未命中即中断，拒绝静默跳过（案例四） | 案例四 |
| **外部锚点断言测试** | 用不可伪造的事实（官方条数/公开总数）做测试断言，同源自证无效（案例一、二） | 案例一 |
| **git 三方对质** | 提交说明、diff 文件清单、历史版本文件内容互相对质，"宣称修复"以 diff 为准（案例四） | 案例四 |

使用顺序建议：先让 bug 变**可复现**（最小样本/干净环境），再让它变**可观测**（数字
锚点/标记核查），最后让它变**不可回归**（外部锚点断言进测试、CI 门禁兜底）。

## 面试话术：每个案例的 30 秒口述版

> **案例一**："我的法律语料管线首跑丢数据：官方 700 条只解析出 657，差 43 条而且零报错。
> 我逐行复刻解析逻辑排除单行匹配问题，再用 9 行最小样本复现，发现状态机只在'下一条
> 出现'时收尾当前条文，章标题一来就把没入库的条文当脏状态丢了——每章最后一条被吞，
> 43 条正好是各章末条之和。修法是所有边界转移先 append 再重置，并加了一条用官方
> 总数 700 做锚点的守恒测试。"

> **案例二**："条号'第1062条'转中文时我踩了连环坑：先因只写了百位分支直接 IndexError；
> 补上千位后又输出'一百零十'——中文数字的'一十''补零'是文化规则不是位置计数。更糟
> 的是仓库里有两份各自漂移的实现。我把转换合并成一份，用 1 到 1260 全量回环穷举验证，
> 还发现回环测不出书写规范错误——宽容解析让'一百零十'也能算回 110——所以又拿官方
> 语料原文做了 700 个条号的交叉比对才敢收工。"

> **案例三**："有一次本地 pytest 109 个全绿、push 后 CI 秒红。看 Actions 日志发现挂的
> 是 pytest 之外的第二条门禁命令，NameError——我重构硬编码路径时引用了 main() 里的
> 局部变量 settings，而且藏在 hybrid 分支里，跑不到就不炸，测试也不覆盖脚本。修复只
> 是加了个参数，但教训固化成了纪律：CI 里每条命令都必须在本地逐条跑过。"

> **案例四**："我在 Git Bash 里用 heredoc 批量打补丁，反斜杠转义被静默吃掉一层，有次

> 未命中即中断、修完按标记 grep 清单逐一核查——'脚本跑完了'不等于'补丁打上了'。"
