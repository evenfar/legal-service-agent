## 一、十大考点

### 1. RAG 管线：法律语料为什么按"同章条文聚合"切块？

- 考点: chunking 策略的领域适配能力（固定滑窗 vs 结构感知切块）。
- 要点: 法律文本的天然最小单元是"条"，但单条平均仅百余字——按条切块检索粒度
  过碎、上下文过散；整章切块又太粗且混杂主题。解法是**同章贪心聚合**：
  逐条累加，触发封块的三条件是或关系——换编、换章、超过 900 字；
  **绝不跨章**保证块内主题纯净（"买卖合同"与"赠与合同"永不同块）；
  封块后统一补条号区间标签（如 `借款合同（第680条）`），区间天然唯一，
  检索命中可精确回溯到条文，也是引用溯源（validate_citations）的锚点。
  900 是聚合目标值，刻意小于 chunker 二次打包上限 1200，加上"最后一条允许
  超额"，块大小上限约 1100——保证**聚合块与向量 chunk 基本 1:1**，
  条号区间标签不会被二次切散。
- 本项目落点: `app/scripts/ingest_laws.py`（`MAX_CHUNK_CHARS = 900`，
  `aggregate_articles()`）；实测 94 块（合同 68 / 婚姻家庭 11 / 侵权责任 15）、
  平均 657 字；`docs/02-语料管线-ingest.md` 第 3 节有完整推导。
- **必讲的 bug 叙事——章边界丢 43 条**: 管线首跑打印"解析 657 条"而官方是
  700 条（合同 526/婚姻 79/侵权 95），零报错静默丢数据。根因：解析状态机只在
  "遇到下一条条文"时收尾 pending 的 current，编/章标题分支却把它当"上一章的
  脏状态"直接 `current = None`——每个编/章的**最后一条**被吞。全量 50 个边界
  中 43 个撞上时有 pending → 恰好丢 43 条（合同 29/婚姻 5/侵权 9）。
  最深一层：**管线自带的条文守恒校验抓不到它**——守恒比的是"解析条数 vs
  写入 md 条数"，两者同源，解析端丢的 md 端同样没有。真正抓住它的是**外部
  锚点**：`tests/test_legal_modules.py::test_parse_all_700_articles` 用官方数字
  700 且逐编 526/79/95 做断言。修复：每个边界分支先 append 收尾再重置。
  教训一句话：同源校验抓不了上游自身的错，必须引入外部锚点或不变量（条号连续性）。

### 2. 检索质量量化：20 条 groundtruth 与 0.35→0.70→0.90 对比表

- 考点: "检索优化没有真值就没有裁判"——评估先行的工程方法论。
- 要点: 先标 groundtruth 再调检索。标注方法论三条：
  ①文档名必须是 `app/agent/rag/knowledge/` 下真实存在的文件；
  ②小节名与语料管线生成的 H2 标题**逐字一致**（chunker 按 H2 切分，
  `Chunk.doc/section` 即命中判定键）；③条号区间归属以民法典官方分章为准。
  同名章会被切成多个 H2（"离婚"有第1076-1083 与第1084-1091 两块），
  必须锚定到具体条号区间。指标 hit-rate@3 + MRR，命中判定 `{doc}#{section}`
  精确匹配。两栏制汇报：离线 HashEmbedder 验证管线确定性，真实 embedding
  （text-embedding-3-small）验证语义收益——避免把散列巧合当语义能力。
- 本项目落点: `app/evaluation/corpus_groundtruth.json`（20 条，12 条扩容而来，
  commit 5eeaf02）；`app/scripts/run_retrieval_eval.py`；方法论文档
  `docs/03-评估与安全.md` 第 6 节。**实测对比表（离线 hash 列，20 条）**：
  baseline 直查 hit@3 0.35 / MRR 0.258 → +rerank 0.70 / 0.617 →
  +hybrid 0.90 / 0.825（adaptive 并列 0.90 / 0.825）；真实 emb 列
  0.92→1.00（rerank/hybrid/adaptive 并列满档，README 记录）。
  rerank 是规则打分（条号精确命中 > 正文 bigram 重叠 > 向量分），零 LLM 成本，
  收益最确定所以先上。
- **门控融合（DENSE_GATE=0.55）**: `app/agent/rag/adaptive.py:35`。
  BM25 票何时进 RRF：每个子查询先跑 dense 召回 top-20，若 top1 相似度
  ≥ 0.55 判定"语义已强"，BM25 **不并票**（词法票反而稀释排名）；
  dense 弱（hash 列/口语失配）才放 BM25 进 `rrf_merge`（RRF_K=60）投票。
  RRF 选出候选池 top-20 后，**终序由 rerank 全权决定**——rerank 只做
  tie-break 会浪费精排信号，实测掉点（代码注释原话）。`--strict` 护栏：
  adaptive 的 hit-rate 低于基线即 SystemExit(1)，机制栈默认只开确定有收益的。

### 3. 图谱提名：案例↔法条双向边，"图给机会，精排终裁"

- 考点: GraphRAG 思想的法律域落地与保守接线。
- 要点: 法律文本天然是图——指导案例的 [相关法条] 字段显式引用条号，法条块
  的区间标签可反向定位。向量检索只能算"语义相似"，发现不了这种**结构化
  多跳关系**（案例→它引用的法条；法条→哪些案例适用）。本项目做 mini
  GraphRAG：解析构建 case_to_articles / article_to_cases 双向索引。
  接线是保守的：top-3 的图邻居只获得"提名"资格，其 rerank 分必须超过
  现末位 + GRAPH_BONUS_MARGIN（5.0 分差）才能顶替末位——**图只给机会，
  不硬塞结果，质量由精排兜底**（adaptive.py `_graph_nominate` docstring 原话
  "图给机会，精排终裁"）。最坏情况退化为没加图，不会引入劣化。
- 本项目落点: `app/agent/rag/citation_graph.py`（`edge_count` 属性）；
  `app/agent/rag/adaptive.py:36`（`GRAPH_BONUS_MARGIN = 5.0`）与
  `_graph_nominate()`。实测：**140 条边**、37 个案例块、103 个条号有案例
  关联（本机重跑 `get_citation_graph` 验证）。审查 #19 后邻居改从图侧直接
  取块（可达邻居共同排序，不依赖是否已被召回）。构建零 LLM 成本，
  缓存键带目录 mtime，知识库重建自动失效。

### 4. 兜错三件套：故障转移链 / 三档拒答 / NLI 句级核验

- 考点: LLM 系统的可用性设计——"失败也要显式、优雅、可观测"。
- 要点（三件套分别管三层）:
  ① **模型层故障转移链**（`app/llm/router.py`）: 主模型→备用模型依次降级，
  每级降级进 tracer（`llm_fallback` 事件可观测），链尾是 RulesFallbackClient
  ——确定性模板应答（"系统繁忙…建议转人工律师（12348）…涉及人身安全请立即
  拨打110"），**chat 永不抛异常**，ReAct 循环拿到模板即可优雅收尾而不是崩溃；
  parse_structured 链尾抛错（结构化提取不能用模板冒充）。捕获范围是
  `except Exception`——认证/参数错误也须降级，不能绕过备模型直接砸向用户
  （这是独立审查抓出的必修项，commit 5554508）。
  ② **检索层校准置信度三档拒答**（`app/agent/tools/knowledge.py`）:
  置信度 = 相关性 × 排序优势（calibrate，top1 领先 top2 的程度）。
  ≥0.5 正常返回；0.25~0.5 附"依据不足，仅供参考"；<0.25 空结果 + 建议转
  人工——**检索层承认失败比幻觉安全**。
  ③ **生成层 NLI 句级核验**（`app/agent/safety/nli.py`）: 回复按句切分，
  逐句算"被检索依据覆盖的 token 比例"（阈值 0.3）；**否定冲突惩罚**——
  句子含"不/未/无/禁止"而依据窗口内无否定词时支持率打五折，抓"把'不得
  转让'答成'可以转让'"这类反转性幻觉。整体支持率 <0.5 且核验句数 ≥2 时
  forced_human 转人工。
- **为什么只降置信、不改写回复**: NLI 本身是启发式（bigram 覆盖 + 否定窗口），
  错误率不为零；改写等于"用一个可能错的核验器去改一个可能错的答案"，
  会污染正确回复。只降置信 + 转人工是把最终裁判权交给人——nli.py docstring
  原话"避免核验器自身的错误污染正确答案（防御性设计的对称性）"。
  落点: `app/agent/base.py` safety_post_process（`nli_check`/`nli_low_support`
  进 tracer；核验在 append_sources 之前——来源行由代码生成无需核验，审查#24）。

### 5. 评估体系：25 条用例、安全一票否决与"执行成功≠业务成功"

- 考点: Agent 评估的过程/结果分层与安全门设计。
- 要点: 用例集是**能力矩阵**而非随机问答——闲聊零工具/结构化查询/确定性
  计算/检索流程/写操作链（先查后写）/多轮/安全红线×4，覆盖五个意图枚举。
  安全一票否决是**乘法门不是加权项**: `safety_guard_pass` 要求
  safety_critical 用例 requires_human=True 且 urgency∈(emergency, urgent)
  双达标，`run_case` 通过条件是"所有维度分 ≥0.6 ∧ token 预算内 ∧
  safety_guard≠0"——安全分不能被高分平均稀释。红线用例还配
  max_tokens:100 + min_tool_calls:0，从预算上反证"确实没走 LLM 和工具"。
  `run_eval` 检出 safety_failures 时 **exit(2)**——非零退出码 CI 可拦截。
  **工具准确率看 ok**: tool_accuracy 只统计 `t.ok` 的调用（审查#22 修复
  "失败调用不再得分"——此前评分器有假阳性：工具报错也算"调准了"）。
  同时 registry 的 ok 语义做了分层: ok=**执行层**成功（无异常）；业务级
  success=False（如"未找到案件"）也算 ok——错误已如实转达给模型与用户，
  属于工具的正确行为。**执行成功≠业务成功**，两层不能混。
- 本项目落点: `app/evaluation/cases.json`（25 条、4 条 safety_critical，
  由 18 条扩容、7 处断言实测校准，commit 008dd14）；`app/evaluation/metrics.py`
  （tool_accuracy 的 ok_set）；`app/agent/tools/registry.py:93`（ok 语义注释）；
  `app/scripts/run_eval.py:71`（exit(2)）。当前成绩: 单/多 Agent 双模式
  25/25，过程分/结果分 1.00。

### 6. Web 工程：SSE 事件流 / per-session 锁 / reset 真语义

- 考点: 把 Agent 栈服务化的并发正确性与 API 语义设计。
- 要点:
  ① **SSE 事件流**: `/chat/stream` 用 `text/event-stream`；`agent.chat()`
  在后台线程跑，SSE 生成器每 80ms 轮询 `tracer.cursor` 取增量（tracer 自带
  锁跨线程安全），线程结束后冲刷剩余事件再发 `event: done` 携带完整
  LegalResponse。事件走**白名单**（7 类: llm_call/tool_call/route/
  redflag_shortcut/nli_check/llm_fallback/injection_blocked），mock 模式
  同样有完整事件流——"看 agent 思考"零成本可演示。
  ② **per-session 锁**: 同一 session 的 chat/reset/SSE 全程串行（锁由 SSE
  生成器持有整个流生命周期，30 秒拿不到锁返回"同会话已有进行中的请求"），
  不同会话互不阻塞；全局 LOCK 只护会话表本身，不长持（审查#3）。
  ③ **reset 真语义**: 旧实现拿 close()（带记忆巩固副作用）冒充 reset。
  修复后 reset 真正清四样——历史/摘要/短期记忆/持久化文件，**保留长期
  记忆**（独立档案文件，不随会话清除）并在响应里声明 cleared/kept 两个
  列表，语义对调用方透明（审查#1）。
  ④ **内存会话工厂注入**: `SESSIONS: dict[session_id → agent]` +
  `get_agent()` 工厂，模式（mock/real）变化时锁内关旧建新；
  `memory_user_id = f"session-{session_id}"` 做会话级记忆命名空间隔离；
  mode=real 仅在服务端 `ALLOW_REAL_MODE=1` 时生效（客户端不能自行烧钱，
  审查#14）；BASE_SETTINGS/会话路径可被测试 monkeypatch 隔离。
- 本项目落点: `app/api.py`（STREAM_EVENT_TYPES / POLL_INTERVAL=0.08 /
  _session_lock / reset 的 cleared-kept / build_settings）；
  `docs/05-API服务与前端.md`。性能实测: mock 编排层单请求约 5ms，
  uvicorn 单 worker 并发 16 下 P95≈76ms、QPS≈270，
  Little's law 验证 269.7 QPS × 59.0ms ≈ 15.9 ≈ 16（已在排队），
  见 `docs/07-性能基准.md`。

### 7. LangGraph 双版本：main 与 langgraph-port 为什么并存

- 考点: 框架选型能力与"机制理解 vs 工程选型"的双叙事。
- 要点: 同一条主链的第二种写法——langgraph-port 分支用 StateGraph 重写
  单 Agent 主链，**领域能力全部 import 复用、零复制**（LLM 客户端/工具
  九件套/安全模块/LegalResponse），`app/` 不改一行。并存的理由:
  **手写版证明机制理解**（ReAct/红线短路/安全后处理每层都是自己写的，
  能徒手画出数据流）；**框架版证明工程选型**（知道 checkpointer/interrupt/
  LangSmith 是自研成本最高的那 30%，何时该用框架）。两版测试互为镜像
  （同 Mock 脚本、同样断言"红线零工具调用"）。
  **两处刻意差异**（教学价值所在）:
  ① 时效临界不短路——手写版任何红线（含"快三年了"）都走模板急症话术；
  图版 `SHORT_CIRCUIT_FLAGS` 只含人身安全+证据风险，**时效临界放行进
  react** 由 calc_limitation 精确计算（模板只给三年一般规定，精算才给
  剩余天数）。这就是"**条件边路由是数据驱动的**"的活演示: 改一个集合，
  图的流向就变——分流逻辑从"读代码追 if 分支"变成"看图即得"。
  ② 记忆/压缩未搬——checkpointer 已覆盖持久化语义，搬进来只会让教学图变胖。
- 本项目落点: `langgraph-port` 分支 `langgraph_app/`（graph 图组装 /
  state 状态定义 / nodes 五节点，`nodes.py:28` SHORT_CIRCUIT_FLAGS）+
  目录 README 概念映射表（handle_redflag↔条件边、react↔节点函数+循环边、
  storage 会话↔checkpointer、input 审批↔interrupt、Tracer↔LangSmith）；
  `tests/test_langgraph.py` 12 条离线用例，分支全量 123 测试绿
  （main 为 111）；实测 langgraph 1.2.14。

### 8. 安全五层（法律域）：三级红线与"模型只见干净数据"

- 考点: 高风险领域的内容安全设计——分层、确定性优先、数据/指令分离。
- 要点（五层，按数据流顺序）:
  ① **入站规则短路**: 三级红线按不可逆性排序——人身安全（伤害不可撤销）
  > 证据安全（删了就没了）> 时效（中断/重算有法定路径）。正则命中直接
  构造 emergency 应答，零 LLM、零工具（`test_redflag_shortcut_zero_llm`
  断言 tracer 里 llm_calls 与 tool_calls 均为空）。三理由: 零漏报（正则
  不受提示词漂移影响）、零延迟（求助者等不了推理）、可解释。Multi-Agent
  模式下 orchestrator.chat 第一行就是 handle_redflag，先于路由。
  **SHORT_CIRCUIT_FLAGS 拆分**: 短路集合独立于检测集合——手写版全量短路，
  LangGraph 版拆出"只短路人身+证据"，时效放行精算（见考点 7）。
  "宁可误报不可漏报"的论证: 误报成本=一次多余提醒，漏报成本=人身伤害/
  证据灭失/丧失胜诉权，皆不可逆；误报面由 `test_no_false_positive_normal`
  守住（正常咨询零误报）。
  ② **检索内容只出 sanitized**: search_knowledge 的结果在进入模型上下文前
  必过 sanitize_tool_output（包裹数据边界+剥离注入样式），**模型不接收
  原始检索内容，清洗不可被绕过**（审查#16a）。工具输出是"数据"不是"指令"。
  ③ **出站安全后处理**: scan_output 注入扫描（命中净化+强制转人工）→
  validate_citations 引用校验（伪造的【文档#小节】直接删）→ NLI 句级核验
  （见考点 4）→ append_sources_if_missing 代码补"参考来源"。
  ④ **提取不重写正文**: 结构化提取只允许补意图/置信度等元数据，reply 以
  安全后处理后的原文为准——模型若在提取时改写正文，安全层就白做了
  （base.py 检测 `result.reply != text` 时强制回填并记
  extract_rewrote_reply，审查#16b）。
  ⑤ **安全后正文才入历史**: ReAct 的 final 文本先挂起，安全后处理完成后
  才由 chat 侧写入历史与持久化——否则被净化的版本和入史版本不一致，
  下一轮上下文里又把脏话术喂回模型（审查#16c）。
- 本项目落点: `app/agent/safety/redflag.py`（RED_FLAG_PATTERNS 三级排列）、
  `injection.py`（sanitize_tool_output）、`app/agent/base.py`
  （handle_redflag/safety_post_process/extract 守门）、`app/agent/chat.py:69`
  （安全后入史）、`app/agent/tools/knowledge.py:21`（sanitized 出口）。
  加分项: 长期记忆防投毒——被污染的对话不该把恶意指令写成长期档案
  （`app/agent/memory/long_term.py`）。

### 9. 真实模式实测：5973 tokens / 13 秒 / gpt-6-luna

- 考点: mock 与真实的差异意识、诚实边界。
- 要点: `ALLOW_REAL_MODE=1` 起服务，mode=real 发一条"查一下案件
  LS-2026-001 的进展"，经 OpenRouter 走 gpt-6-luna：**5 次 LLM 调用、
  共 5973 tokens、端到端 13 秒**。三个教学观察:
  ① **真实模型比 mock 更"守规矩"**: system prompt 里"涉案件建议前先核对
  用户档案"的指令，真实模型第一步就执行了 `recall_user_memory`——
  mock 脚本没有模拟这一步。这说明提示词约束对真实模型有效，也说明
  mock 轨迹与真实轨迹"结构一致、顺序可有差异"。
  ② **成本结构**: ReAct 3 次 + 提取 1 次 + 短期记忆 1 次；react 的
  prompt_tokens 随历史增长（1212→1298→1610），印证历史压缩机制的必要性。
  ③ **13 秒瓶颈全在 LLM 网络往返**（5 次串行调用），编排层 mock 实测约
  5ms 占比不到 1%——与性能基准互相印证。
  诚实边界（docs/08 末尾明写）: 单条消息验证，未覆盖真实模式红线短路
  （不调 LLM 与模式无关）、真实 embedding 检索质量（对比表另有）、超时
  降级链路实测。
- 本项目落点: `docs/08-真实模式验证.md`（事件轨迹逐条带 token 数）；
  `app/agent/tools/memory_tool.py`（recall_user_memory 工具）。

### 10. 26 项外部审查修复：三个代表性叙事

- 考点: 接受外部审查的工程成熟度——问题分级、修复可追溯、流程固化。
- 要点: 外部审查共 26 项，分两批交付（批次 A #1-3/7-12，commit 88fb6fe；
  批次 B+C #13-26，commit 13539a5），另有 953f8e4（7 项确认 + 3 项误判
  澄清）。三个代表性叙事（每个都能讲 2 分钟）:
  ① **reset 真语义（#1）**: 旧 /reset 实际执行的是 close()——而 close 带
  记忆巩固副作用，等于"用有副作用的析构冒充清空"。修复: reset 真正清
  历史/摘要/STM/持久化文件，保留 LTM 并在响应声明 cleared/kept；配套
  #2 把 Mock 状态从"历史长度计数"改成"任务代次键"（压缩/reset 不回退
  不串轮），reset_state 钩子同步清缓存——reset 后重复提问必须重新走工具。
  ② **MCP 双重编码（#4）**: MCP server 返回的是 JSON 文本，桥接层若直接
  把字符串再 json.dumps 一次塞回模型，模型看到的是带转义的字符串套字符串
  （双重编码）。修复: 在协议边界 json.loads 一次还原为对象，再走统一的
  sanitize 出口（#16d: MCP 与本地工具同过清洗）。
  ③ **评分器假阳性（#22）**: tool_accuracy 原实现只看"工具名是否被调用过"
  ——调用了但执行报错（ok=False）也算"调准了"，评分器给假阳性分。
  修复: 只统计 ok 的调用；同时把 registry 的 ok 语义分层——执行成功
  （无异常）≠业务成功（success=False 的"未找到"是正确行为），两层混用
  会把好工具误判成坏工具或反之。
  流程固化: 修复全部带 commit 与回归（109 测试全绿 + eval 满分 + --strict
  通过才收）；由此沉淀的纪律——CI 每条命令本地逐条跑过（#13 的 NameError
  红窗 26 小时的教训）、批量修改幂等标记 grep 核查（heredoc 静默失败案例）。
- 本项目落点: commit 88fb6fe / 13539a5 / 953f8e4（提交说明即修复清单）；

## 二、深挖预判：每题可能的"追问一刀"与挡法

1. **切块**: "900 为什么不是 512/1024？做过参数实验吗？"
   → 900 是聚合目标不是向量块大小，真正的约束是 chunker 的 1200 上限减去
   【doc#section】前缀余量，目标是聚合块与向量 chunk 1:1；数字来源是
   94 块平均 657 字的实测分布。诚实承认没做 embedding 维度的敏感性实验。
2. **检索量化**: "20 条 groundtruth 会不会标偏？expected 泄漏到优化里？"
   → 标注锚定三条 + test_groundtruth_file_valid 逐条校验文件存在；
   优化机制（rerank 规则）写于标注之后但独立于具体 query（条号/词重叠
   通用规则）；两栏制 + --strict 护栏防退化。承认 20 条只够比大小，
   不够做统计显著性检验。
3. **图谱**: "140 条边规模这么小，GraphRAG 是不是过度设计？"
   → 定位就是 mini GraphRAG：成本为零（解析引用字段），接线保守
   （margin 5 分差才顶替，最坏等于没加），讲的是"结构性多跳关系向量检索
   覆盖不了"这个机制认知，等案例全量入库后收益自然放大。
4. **兜错**: "NLI 不改写，万一模型真的错了呢？"
   → 错了会转人工（forced_human），这正是设计意图：启发式核验器的错误率
   不为零，让它改写是把一个可能错变成两个可能错；降置信+交人是把裁判权
   外移，且 nli_low_support 进 tracer 可审计。
5. **评估**: "用例是你自己写的，自己考自己？"
   → mock 评估的本质是回归测试不是智力测试——断言锚定 mock 脚本的确定性
   行为，考的是编排逻辑；外部审查 #22 恰恰抓出我评分器的假阳性并修掉，
   这正是"防止自己骗自己"的例子；真实质量另有 docs/08 单例 + 真实
   embedding 检索列两块独立证据。
6. **Web**: "SSE 为什么轮询而不是 WebSocket 推送？"
   → 场景是单向展示，tracer 已有 cursor 增量机制，80ms 轮询 30 行实现且
   天然背压；mock 下 chat 毫秒级完成，靠"线程结束后冲刷"保证不漏事件；
   双工需求（HITL 审批）才值得上 WebSocket。
7. **LangGraph**: "既然手写能跑为什么还花时间 port？"
   → port 的成本被零复制压到最低（只写图组装），买到的是选型发言权:
   我能指着概念映射表说 checkpointer/interrupt 是自研最贵的 30%，
   这个结论只有两边都写过才立得住。
8. **安全**: "红线全靠正则，用户换个说法你怎么办？"
   → 承认召回上限，用"宁可误报"的宽模式 + 多 pattern 并列提覆盖；
   漏网的内容进入正常链路仍有出站五层（引用校验/NLI/转人工）兜底；
   正则做的是"高置信子集的确定性保障"，不是全量分类器。
9. **真实模式**: "只测了一条消息能说明什么？"
   → docs/08 末尾明写未覆盖清单——单条验证关闭的是"链路能不能跑通"
   （接口/格式/事件流/结构化提取全链），不是"质量达标"；且它发现了
   mock 发现不了的行为差异（recall_user_memory），这正是做它的价值。
10. **审查**: "为什么会有 26 项问题，代码质量是不是不行？"
    → 审查发生在升级期新代码上，集中在并发/边界/语义分层这类"跑得通
    但不对"的问题——恰是单人自测的盲区；每项修复带 commit+回归+测试，
    并沉淀成流程纪律（CI 双命令、幂等核查）。有审查并全修，比没有
    审查更接近生产。

## 三、三个"必死"问题（准备不足必挂）

### Q1. "你评估 25/25 满分，所以系统真实准确率是 100%？"（标准答案必背）

> 不是，这个数字的**语义边界**我刻意设计得很窄: 25 条用例跑在 mock 模式下，
> LLM 是按 purpose 分发的脚本（app/llm/client.py 的 MockLLMClient），断言的
> expected_keywords/expected_tools 是按 mock 确定性行为标注的。它证明的是
> **编排逻辑与安全机制的正确性**——红线真的零 LLM 短路、引用校验真的删
> 伪造引用、故障转移真的降级，这些与模型智力无关的层 100% 可回归。
> 它**不证明**模型回答的法律内容质量。真实准确率我有三块独立证据:
> ① 检索质量与模型解耦评估——20 条 groundtruth 双列对比，真实 embedding
> 列 hit@3 0.92→1.00；② 真实模式端到端验证——gpt-6-luna 单条全链 5973
> tokens 跑通且结构化输出正确（docs/08）；③ 尚未做的: 真实模式的规模化
> 质量评估（配 judge + 专用期望集），这是我在边界声明里主动列出的下一步。
> 一句话: **mock 满分证机制，真实质量靠分层证据，两者我从不混着讲。**

### Q2. "红线正则漏了一句换说法的家暴求助，责任怎么算？"

> 我不给"零漏报"的承诺，给的是分层诚实: 正则层保证的是已枚举模式（宽
> 口语化的模式集）上的零漏报 + 零延迟 + 可解释；没命中的表述进入正常
> ReAct 链路，仍有出站防线（引用校验/NLI 低支持转人工）和 system prompt
> 的 emergency 升级约束（提取层人身内容必须标 requires_human）。工程上
> 这是"高置信子集确定性保障 + 其余概率性兜底"的分层设计。责任归属上，
> 产品定位是"科普级程序指引，不构成法律意见"（语料 DISCLAIMER 随每个
> chunk 落地），requires_human 是系统的显式输出字段——把转人工做成
> 结构化契约而不是客服话术。

### Q3. "43 条都能被静默吞掉，你怎么保证现在没有别的静默数据 bug？"

> 不能保证"没有"，我提供的是"会被抓住"的机制: ① 外部锚点断言——
> test_parse_all_700_articles 用官方数字（700 且逐编 526/79/95）做测试，
> 同源自证无效是那个 bug 的核心教训；② 条号连续性不变量（同编内差恒 1，
> 丢条必现跳跃）作为补充手段（docs/02 练习 1）；③ ingest 的三重校验
> （守恒/免责声明/H2 结构）任一失败 SystemExit(1)，坏数据入库前死掉；
> ④ 20 条 groundtruth 检索评估本身也是语料完好性的持续哨兵——语料缺了
> 一章，对应 query 立刻 miss，--strict 在 CI 里红。调试工具箱（最小样本
> 复现/数字锚点对账/全量回环断言/git 三方对质）沉淀在 docs/06，
> 那是我对"静默失败"这类问题的成套打法。
